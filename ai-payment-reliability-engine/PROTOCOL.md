# PROTOCOL.md — Evaluation Protocol for the AI Payment Reliability Engine

This document freezes the research questions, metrics, data splits, and
statistical procedure used to evaluate the classifier + RCA + remediation
pipeline against RCAEval and OpenRCA-derived incident data. It is the
contract between experiment code and the taxonomy in `data/taxonomy.yaml`:
any change to fault_class/payment_sli/sli_map that would invalidate a
metric definition below requires a new version of this document.

## Research Questions

| ID  | Question | Mode |
|-----|----------|------|
| RQ1 | How accurately does the ML-only classifier assign the correct `fault_class` label compared to RCAEval/OpenRCA ground truth? | Offline |
| RQ2 | Does adding the LLM classifier (Groq/Ollama) to the ensemble improve fault_class accuracy and/or severity calibration over ML-only, and by how much? | Offline |
| RQ3 | How well does the mapped `payment_sli` (via `sli_map`) track the actual injected fault's impact on payment-domain metrics, across the five target systems? | Offline |
| RQ4 | Does automated remediation dispatch reduce mean time-to-resolution (MTTR) versus a no-remediation baseline, when run against live/replayed telemetry? | Online |
| RQ5 | Is the end-to-end 5-layer agent loop (classify → RCA → remediate → verify → log) stable and safe (no duplicate escalations, no crash loops) under a sustained incident stream? | Online |

- **Offline**: evaluated against static, pre-labelled RCAEval/OpenRCA cases; no live system under test.
- **Online**: evaluated against a running instance of the target system (Online Boutique, Sock Shop, Train Ticket, OpenRCA Bank, or the OTel Demo) with faults injected live.

## Metric Definitions

- **fault_class accuracy** — exact-match rate between the predicted `fault_class` (from `data/taxonomy.yaml`) and the RCAEval/OpenRCA ground-truth label for the case, over all cases in the evaluated split.
- **Top-3 accuracy** — fraction of cases where the ground-truth `fault_class` appears in the classifier's top-3 ranked predictions (by calibrated probability for ML, by stated confidence for LLM).
- **Severity calibration error (SCE)** — **dropped (A20 review), same reason as escalation correctness below.** SCE was defined as the mean absolute difference between predicted severity rank and "a held-out human-labelled severity rank," but no such label exists — there is no independent ground-truth severity field on `GroundTruth` (`pre/signals/types.py`) to score against; severity is only ever assigned by the triage step under evaluation. The metric was never implemented (nothing in the codebase computes it, and "over all cases where a human label exists" was an undisclosed count of zero). Reinstating it correctly requires designing and labelling an independent severity ground truth per case, held out from triage output, the same way escalation correctness would need a blast-radius taxonomy — out of scope for this submission. Separately, "calibration error" is the wrong name for a rank-difference metric even if the label existed: calibration in the cited literature refers to predicted-probability-vs-observed-frequency agreement, not a mean absolute rank distance, so a reinstated version should be named for what it measures (e.g. "severity rank error") rather than reuse that term.
- **SLI mapping precision** — fraction of predicted `payment_sli` values (via `sli_map`) that match the SLI a human reviewer independently identifies as the one materially degraded by the injected fault.
- **MTTD (mean time-to-detection)** — wall-clock time from `fault_injected` (the ledger row written when a fault is introduced — for the A13 testbed, a flagd flag toggled on) to `incident_detected` (the row written when `pre.verify.kpi_verifier.wait_for_breach` first observes the mapped `payment_sli` outside its objective), averaged over all incidents in an online run. Faults whose SLI never breaches within the breach-watch window (`A13_BREACH_TIMEOUT`) are excluded and reported separately as the missed-detection rate.
- **MTTR (mean time-to-resolution)** — wall-clock time from `incident_detected` to `verification_complete` with `status == "resolved"`, averaged over all incidents in an online run; incidents that never resolve within the run window are excluded and reported separately as the unresolved rate. **`incident_detected` is the sole anchor (A20 review)** — a prior version of this document also named `incident_started` (emitted by `pre/agent_loop.py`, a separate, older logging path) as an alternate, but no MTTR figure anchored there was ever actually computed or persisted anywhere in `results/`; all seven existing A13 run ledgers use `incident_detected` exclusively. There is nothing to recompute or drop. **Right-censoring correction (A20 review).** An incident detected late in the run window can only be counted as resolved if its true resolution time is shorter than the remaining wall-clock time before the run ends (compounded by the mandatory 120 s `SUSTAINED_WINDOW_SECONDS`); an incident detected at the same true severity but needing longer to resolve gets dropped into the unresolved rate instead of contributing its (longer) true duration to MTTR. Averaging only the resolved subset therefore survivorship-biases MTTR low in proportion to how many incidents land near the run-end cap. **Chosen fix: truncation exclusion, not Kaplan-Meier.** For a given run, let `R_max` be the longest resolution time observed among that run's resolved incidents. Any incident — resolved or not — whose `incident_detected` falls after `run_end − R_max` is excluded from the MTTR average entirely (not counted as resolved, not counted as unresolved), since it never had a full `R_max`-length window to resolve within and so cannot be fairly compared to incidents that did. This is reported as a third rate alongside the resolved/unresolved split: the **censored-exclusion rate**. A Kaplan-Meier estimator (treating run-end as right-censoring) would use the excluded incidents' partial data rather than discarding it, and is the more statistically efficient choice if a future run has enough incidents for it to matter — but no online run eligible for reporting has been completed yet, and truncation exclusion is simpler to implement and audit by hand against a run ledger, so it is what this document specifies for now. Silent truncation (using all incidents regardless of when they were detected, the prior undocumented behavior) is not an option.
- **What the seven existing A13 run ledgers are, and why no online result is reported from them (A20 review — stated explicitly here, not left in the MTTR anchor parenthetical above).** `results/a13/*/smoke.jsonl` (seven timestamped directories, 2026-09-10T22:31Z through 2026-09-11T19:24Z) are `scripts/a13_smoke.py` shakedown runs from debugging and fixing A13 testbed under-provisioning, not output from a defined, frozen online-evaluation scenario matrix. Six of the seven predate the "A13: fix testbed under-provisioning" commit and show exactly the failure it fixed (`authorisation_success_rate never breached within 150s`, `incident_detected.success == false`, from services OOMKilling under sustained load); the seventh, run after that fix, is the first ledger where every flag's incident was detected successfully — a testbed-health confirmation, not a scored evaluation run. None of the seven satisfy this document's Stopping Rules as a complete, reportable run, which is why the journal manuscript's RQ4/RQ5 tables read RESULTS PENDING: no online run meeting the protocol above has been executed yet.
- **Sustained recovery interval** — an incident is only marked `status == "resolved"` once the triggering `payment_sli` has stayed continuously inside its objective for `SUSTAINED_WINDOW_SECONDS` (default **120 s**, `A13_SUSTAINED_WINDOW`), sampled every `A13_POLL_INTERVAL` (default 15 s) by `pre.verify.kpi_verifier.wait_for_recovery`. A single in-objective reading is not resolution; any out-of-objective reading resets the sustained timer. `verification_complete` is timestamped at the end of the sustained window, so MTTR includes it.
- **Escalation correctness** — **dropped (A20 review).** The ground-truth "should have escalated" label was defined as SEV-1/SEV-2, but severity is only ever assigned by the triage step under evaluation — there is no independent ground-truth severity or blast-radius field on `GroundTruth` (`pre/signals/types.py`) to score against instead. The metric was never implemented (nothing in the codebase computes it). Reinstating it correctly requires designing and labelling a blast-radius taxonomy per injected fault type across RCAEval/OpenRCA cases, independent of triage output — out of scope for this submission.
- **Availability** — **redefined (A20 review).** Fraction of acquirer-emulator authorization attempts that received an acquirer response (approved or declined) rather than a transport failure, measured as `demo_payment_charge_result_total{acquirer_response_code!~"timeout|unreachable"}` over all attempts (`pre.verify.kpi_verifier.SLI_QUERIES["availability"]`). Previously defined as `GET /health` returning HTTP 200, which cannot fail while the harness process is alive and collides in name with `taxonomy.yaml`'s `frontend.availability`-mapped SLI without measuring the same thing as either. `GET /health` remains in use for the harness-crash abort condition in Stopping Rules below, which is a distinct, legitimate concern (is the harness process alive) — it is no longer called "availability" anywhere a payment-path result is reported.
- **RCA faithfulness** — fraction of an RCA's claims that are (stage 1) grounded in an existing, anomalous evidence-pack item AND (stage 2) supported by that evidence per the **primary judge** (see Faithfulness Judging below). Reported alongside `dropped_claims` (claims discarded for citing unknown evidence IDs).
- **No reported quantity is derived from a pseudo-random draw.** `tests/test_no_random_in_loop.py` asserts that no module reachable from the evaluation entry points imports or calls a random number generator, and runs in CI on every commit.

## Faithfulness Judging (A9)

Two-stage check per claim (`bench/faithfulness.py`):

- **Stage 1 — existence + anomaly.** Every cited evidence ID must exist in the A8 evidence pack and have anomaly score ≥ `MIN_ANOMALY_SCORE` (0.3). Deterministic. Gates.
- **Stage 2 — entailment.** Does the rendered evidence support the claim?

Stage 2 uses **two judge backends**, with distinct roles:

| Backend | Model | Role | Gates faithfulness? |
|---|---|---|---|
| **chat-model judge** | `bench.faithfulness.DEFAULT_CHAT_JUDGE_DIGEST` (currently `ollama:qwen3.8:27b`) | **Primary.** Its score + threshold define the reported RCA faithfulness metric and are the automated side of the human-agreement (Cohen's κ) study. | **Yes** |
| **NLI cross-encoder** | `cross-encoder/nli-deberta-v3-base` | **Comparison point / documented failure — see the characterization below; it is not a faithfulness judge on this data.** Reported next to the primary judge to quantify the gap; never the headline number. | No |

Rules:

- The chat-judge model **family must differ from the RCA generator's** (`pre.agents.rca.RCAAgent.generate` defaults to `ollama:llama3.1`, llama family → judge is qwen family) so the judge is not grading a sibling model's output. If the RCA model changes, the judge model must be re-checked for family separation.
- **Corrected (A20 review):** the chat judge is run **once per claim** (temperature 0), not 5 times as an earlier version of this document stated. Checked directly against `bench/faithfulness.py` and the canonical faithfulness run (`docs/faithfulness/judge_scores.jsonl`, generated 20260910T170647Z at git_sha ce9491b1, 67 rows): there is no repeat-calling loop in the code, and the data has exactly one row per distinct `(case_id, claim_text)` pair with no evidence any claim was ever judged more than once. The "5 times, distinct seeds" language was never implemented and is removed rather than justified after the fact; temperature-0 repeats would in any case be pointless against sampling variance and were never motivated as a guard against backend/batching nondeterminism instead. The NLI judge is deterministic and also run once.
- **Truncated / unparseable judge replies are never trusted.** If the model's reply is cut at the token limit (`LLMResponse.truncated`, from Ollama `done_reason == "length"` / OpenAI `finish_reason == "length"`) the call is retried once at 3× the budget; if it is still truncated, or the reply cannot be parsed, the claim's stage-2 result is marked invalid (`stage2_valid == False`). Invalid claims are **excluded** from `stage2_pass_rate` and `avg_faithfulness_score`, counted in `n_stage2_invalid`, and count as not-faithful for `overall_faithful_rate`. A non-trivial `n_stage2_invalid` is reported as a run limitation.
- **NLI score is raw `P(entailment)`** from the 3-class head.
- **What the NLI judge can and cannot do (probed, `tests/test_faithfulness.py::test_nli_capability_*`):** on general-language pairs its entailment head works normally ("a man playing guitar on stage" ⊨ "a person performing music" → P(entail) ≈ 0.98). On this task it recognises a claim only when the claim is **at most one lexical / directional substitution away from the evidence's literal text** — "spiked to 100.0" ⊨ "rose to 100" / "CPU increased" / "reached 100 percent" / "experienced high CPU usage" (all P(entail) > 0.9). It **cannot** do the abstractive or multi-hop step that essentially every real RCA claim requires:
  - naming a failure mode the evidence implies but does not state — "was saturated", "was fully utilised", "had a memory leak", "is a bottleneck" → `neutral`, P(entail) ≈ 0 (even though it separately accepts "100 percent" ⊨ "saturated" — it will not chain "spiked to 100.0" → "100 percent" → "saturated");
  - interpreting the z-score — `z=108.5` does **not** entail "far above baseline" / "deviated far from its normal range" for this model.
  On our telemetry-notation evidence it therefore behaves as a **shallow restatement detector, not an entailment judge over RCA reasoning**: it scores ~0 for any claim that *characterises* the failure rather than *echoing the metric*. All 10 cases sampled for this study (`docs/faithfulness/`, generated 20260910T170647Z at git_sha ce9491b1) remain **in** the study; `RE1-OB_cartservice_disk_1` is a documented pipeline failure, not an exclusion — its synthesized alert matched an unrelated `currencyservice` memory signal instead of the case's actual `cartservice` disk fault, so evidence ranking returned nothing and the RCA model's resulting claims were all correctly dropped for citing evidence never shown to it (zero claims recorded for this case, contributing nothing to either judge's per-claim numbers — see the `mis_synthesised` finding below for why this is not a one-off). Its mean P(entail) on hand-written, genuinely-grounded paraphrased control claims (n=9, drawn from the 9 cases that produced usable evidence) was **0.0014** — indistinguishable from its score on adversarial claims (0.000). This is why it is a comparison point only.
- **Alert mis-synthesis (`mis_synthesised`, A20 review) — outranks the faithfulness pass-rate number below.** `bench/run_faithfulness_study.py` now counts, for every case, whether the synthesized alert's matched service (`Alert.service`) equals the case's ground-truth `root_cause_service` (an alert can only be scored this way outside `pre/signals/alert_synth.py` itself, since that module structurally never receives `GroundTruth` — see its isolation-invariant docstring). Measured directly against the 10 real RE1-OB study cases (`data/rcaeval/RE1-OB`, reproducible via `synthesize_alert`): **8 of 10 cases mis-synthesise** — the alert names a service other than the ground-truth root cause (e.g. `RE1-OB_cartservice_cpu_1`'s ground truth is `cartservice`, the synthesized alert matched `redis`). Only 2 of 10 (`checkoutservice_cpu_1`, `currencyservice_loss_1`) matched the correct service. `RE1-OB_cartservice_disk_1`'s zero-claim failure above is not an outlier; it is the one case out of eight where the mismatch also broke evidence ranking downstream. Plainly: **the alert-synthesis step names the wrong service before RCA ever runs in the majority of cases studied**, which is a pipeline-reliability finding independent of and more consequential than the RCA faithfulness pass-rate reported below — a faithful-to-evidence RCA claim can still be reasoning about the wrong service's evidence pack. This is expected in a microservices system where faults cascade (a naive earliest-breach alert will often catch a downstream symptom before the upstream root cause breaches), but it was previously undocumented outside one case, and is now tracked and reported for every run of the faithfulness study rather than surfaced only when it happens to also zero out a case's claims.
- **Alert mis-synthesis confirmed at scale, and scoped against A7/A8 (A20 review).** The 8/10 rate above is not specific to this small study sample: measured against the full 340-case A7 train/val/test pool (`docs/a7_multisystem_training_report.md`), RE1-OB (125 cases) mis-synthesises at 89.6% and RE2-TT (90 cases) at 97.8% — combined, **200/215 = 93.0%** on the two datasets where per-service attribution is actually possible. RE1-SS (125 cases) reads 100% but is excluded from that figure: its raw Prometheus column names (e.g. `carts_container-cpu-system-seconds-total`) never match `pre/signals/rcaeval.py`'s `_METRIC_COL_RE`, so every RE1-SS metric falls back to a synthetic `"cluster"` service regardless of alert correctness — a data-adapter gap, not evidence about alert-synthesis behaviour, and a separate, pre-existing limitation of its own. The evidence-ranker's critical-path boost (`EvidenceRanker.boost_graph_path`, see A8) is keyed to this same mis-attributed alert service, though it is architecturally inert for RE1-OB/RE1-SS (no trace-derived topology exists for either — neither dataset ships a `traces.csv`) and empirically changes ranked output in 17.8% of RE2-TT cases (16/90, measured by comparing boosted vs. unboosted `featurize_pack` output), with no consistent directional bias toward or away from the correct metric family. The faithfulness study reported above is built entirely on RE1-OB cases, which carry no trace data and therefore have zero exposure to this boost-leak channel — its faithfulness numbers are not confounded by it, even though the alert-synthesis mis-attribution itself still is (see above).
- It does retain **high precision on contradictions and unrelated claims** (both → P(entail) ≈ 0), so a *high* NLI score is still meaningful (near-verbatim support); a *low* one is not (could be fabrication, could be a true abstractive claim).
- **NLI scores are never averaged into a faithfulness statistic** — a low one carries zero information. `compute_faithfulness_metrics` computes `avg_faithfulness_score` / `stage2_pass_rate` / `overall_faithful_rate` from the **chat judge only** (all `None` with a caveat if no chat-judge scores are present). NLI enters exactly one aggregate, `nli_corroboration_rate`: the fraction of chat-faithful **production** claims (`kind=='rca'`; control/adversarial claims are judge-calibration probes, excluded from this denominator) that NLI *independently* scores ≥ `NLI_CONFIRM_THRESHOLD` (0.8) — a one-directional corroboration signal. The same computation over all populations is retained for reference as `nli_corroboration_rate_all_populations`, never cited as the primary figure. The earlier `0.5·(1 + P(entail) − P(contra))` blend was rejected for parking every `neutral` claim at the 0.5 pass/fail threshold; an interim `avg_entailment_score` that averaged NLI's ~0s into a reported mean was likewise removed.
- Judge outputs are stored as `results/faithfulness/<ts>/judge_scores.jsonl` (one record per `(case_id, claim_text)`, both judges' scores + raw output + model digests) plus `manifest.json`. `results/` is gitignored, so these per-run directories are ephemeral scratch output, not citable artefacts. The run this document cites is committed at `docs/faithfulness/{judge_scores.jsonl,manifest.json}` (`manifest.json.git_sha` records which commit produced it — currently ce9491b1); re-running the study does not move this citation forward until the committed copy is deliberately replaced. The human-rating study joins on `(case_id, claim_text)` to compute κ **against the chat judge**; NLI agreement is reported as a secondary comparison.

## Train / Validation / Test Splits

- Cases are split **by fault-injection run**, not by individual telemetry sample, to avoid leakage between splits on the same injected fault.
- **Model and split corrected to match the shipped pipeline (A20 review).** RQ1's ML classifier is `pre/agents/training/train_triage.py`'s `train_triage()`: `StandardScaler` + `LogisticRegression(max_iter=1000, random_state=42, multi_class='multinomial', solver='lbfgs', class_weight='balanced')`, with an `IsotonicRegression` calibrator fit on the validation set's predicted-probability-vs-correctness pairs. This document previously named `LinearSVC`, which is a different, separate classifier (`pre.classifier.MLClassifier`, trained on synthetic data for the live agent loop, not on RCAEval ground truth) — not what RQ1 actually evaluates.
- **Split, stated in case counts (A20 review):** 125 total cases (RCAEval RE1-OB, `features.parquet`, per `docs/a7_triage_training_report.md`), split by fault-injection run via `train_test_split(..., test_size=0.2, random_state=42, stratify=y)`: **100 train (80%) / 25 validation (20%)**. The previously-stated 60/20/15/5 percentage split does not correspond to any split this codebase runs, is non-integer at n=125 (15% = 18.75 cases, 5% = 6.25 cases), and was never implemented. **There is no held-out test split and no frozen "final report" set** — the isotonic calibrator and the tau selection sweep are both fit against the same 25-case validation split reported above, and every figure in `docs/a7_triage_training_report.md` (train accuracy, validation accuracy, tau/precision/recall) is a validation-set figure, not a further-held-out test or final-report figure. A 6-case frozen set (5% of 125) is far too small to support a reported figure reliably; rather than reinstate a set this small, this document states plainly that the study has no final-report set, and any future one should be sized and drawn independently of this decision, not retrofitted onto the existing 125-case split.
- OpenRCA cases: used only for validation and test (40% validation / 60% test) since RCAEval provides the primary training signal for the ML classifier's `_TRAINING_DATA`.
- **Splits are stratified by `fault_class` over whichever classes the source dataset actually injects, not all thirteen (A20 review, corrected).** `data/taxonomy.yaml`'s `fault_class` list has 13 entries, but no single RCAEval dataset can reach all of them: `RCAEvalAdapter` supports RE1/RE2 only (RE3's 5 code-level classes — `logic_error`, `concurrency_issue`, `api_compatibility_issue`, `performance_bottleneck`, `exception_handling_error` — are explicitly out of scope), and no real OpenRCA Bank data exists in this repo (its 2 classes, `configuration_error`/`dependency_failure`, are unreachable regardless). That leaves 6 RE1/RE2 classes (`cpu`, `memory`, `disk`, `socket`, `delay`, `loss`) as the practical ceiling — and even that ceiling isn't uniform across datasets: RE1-OB and RE1-SS never inject `socket` faults at all (checked directly against `data/rcaeval/{RE1-OB,RE1-SS}`'s case directories: 5 fault types each — `cpu`, `delay`, `disk`, `loss`, `mem` — with no `socket` case in either, structurally, not by sampling chance), so their ceiling is 5, not 6; RE2-TT reaches all 6. This is why `docs/a7_triage_training_report.md`'s 125-case RE1-OB run reports "Unique classes: 5" — that is the correct, maximum count for that dataset, not evidence of a stratification bug. (`unknown` is separately excluded — per `pre/classifier/taxonomy.py`, it is not a ground-truth fault label, only the classifier's own low-confidence/no-match fallback bucket, so no case is ever ground-truth-labelled `unknown` for a split to stratify by.)
- LLM configurations are never fine-tuned; only prompt and provider selection are evaluated against validation, with test reserved for the final comparison in the paper/report.

## Statistical Procedure

- Significance threshold: **alpha = 0.05**.
- All pairwise comparisons within a given RQ's family of comparisons use **Holm–Bonferroni correction** across that full family, controlling family-wise error rate (A20 review: widened from "pairwise comparisons across LLM configurations," which as stated would have excluded the ablation family, e.g. the A1–A6 system-variant comparisons in `bench/run_benchmark.py`, and the baseline family from correction). This covers, per RQ: LLM-configuration comparisons (e.g. Groq vs. Ollama vs. ML-only, or prompt variant A vs. B), ablation comparisons, and baseline comparisons alike — whichever family of comparisons that RQ's analysis actually runs.
- LLM components are called once per case at temperature 0; no repeat averaging is performed, and no between-repeat variance is reported. The ML classifier is likewise deterministic given `RANDOM_SEED` and is run once per case.
- Reported effect sizes accompany every significance test (Cohen's d for continuous metrics such as MTTR/SCE, Cohen's h for proportions such as accuracy).
- Paired tests (Wilcoxon signed-rank) are used when comparing two classifiers on the same case set; unpaired tests (Mann-Whitney U) are used only when case sets differ (e.g. RCAEval vs. OpenRCA).

## Stopping Rules

- **Offline evaluation** stops once all cases in the frozen test split have been scored for the configuration under test; no early stopping is applied to offline runs since they are not adaptive.
- **Online evaluation (RQ4/RQ5)** stops for a given run when *either*:
  1. 200 incidents have completed the full 5-layer loop (classify → RCA → remediate → verify → log), or
  2. 2 hours of wall-clock time have elapsed since the first incident in the run,
  whichever comes first.
- An online run's **harness is aborted early, and the run excluded from the final report** (logged as a failed run) if `GET /health` fails to return HTTP 200 for more than 60 consecutive seconds — this is a harness-liveness failure, not a signal about the system under test.
- An online run's **incident stream is truncated early** (stop wasting compute on a clearly broken run, not excluded) if more than 3 duplicate PagerDuty escalations for the same `incident_id` are observed. **Unlike the health-check abort above, truncation here does not remove the run from RQ5's report (A20 review)** — RQ5 asks whether the loop produces duplicate escalations, so a run that trips this condition is itself the outcome RQ5 measures, not noise to discard. The run's duplicate-escalation count (accumulated up to truncation) is reported as an RQ5 outcome alongside every other run, with the run explicitly marked `truncated: true` and its completed-incident count noted, so a reader can tell "zero duplicates because the loop is safe" apart from "zero because the run never got that far."
