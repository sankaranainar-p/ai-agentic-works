# ACS Cross-Border Compliance: Python → Java Port

## Context

`acs-cross-border-compliance` is a ~400-line reference implementation
supporting a submitted manuscript ("A Decentralized Agentic Architecture for
Real-Time Compliance and Fraud Detection in Cross-Border Payment Systems").
It simulates a multi-agent pipeline over ISO 20022-style transactions: an
anomaly detector (IsolationForest), a rule-based policy agent, a composite
risk agent, a human-on-the-loop rule, a hashed audit log, and a supervised
XGBoost fraud classifier, all fused by an `ACS_Orchestrator`.

The existing Python implementation (pandas, scikit-learn, XGBoost,
imbalanced-learn's SMOTETomek, matplotlib) is being fully replaced with a
Java 21 / Maven implementation, in the same directory. The Python source is
removed once the Java port is verified working end-to-end against the real
data.

## Goals

- Faithful, functionally-equivalent Java port of every module: data
  loading/merging, feature engineering, all six agents, the orchestrator's
  fusion logic, evaluation, and the report-generating pipeline script.
- Get as numerically close as practical to the existing Python output
  (`reports/metrics_summary.txt`: confusion matrix `[[19669,244],[4025,62]]`,
  `reports/confusion_matrix.png`) by porting algorithms faithfully rather
  than substituting differently-behaved library equivalents, while accepting
  that bit-for-bit parity is not achievable (see Non-goals).
- Preserve the README's existing "known limitation" caveat about
  `velocity_score` / `device_risk_score` / `time_diff` being a provisional
  reconstruction — that caveat is about data/methodology, not language.
- Working `mvn test` and a runnable pipeline that regenerates
  `reports/confusion_matrix.png` and `reports/metrics_summary.txt`.

## Non-goals

- **Bit-for-bit numeric parity with the Python run.** numpy's PCG64 RNG and
  Java's `Random` produce different sequences from the same seed; matching
  them would require hand-porting PCG64, which was explicitly ruled out as
  disproportionate effort. Algorithm-faithful ports (same formulas, same
  tree-building/splitting/interpolation logic) seeded with `42` via Java's
  own RNG is the agreed target — this should land close to the existing
  numbers but not reproduce them exactly.
- Keeping the Python code side-by-side. It is removed after verification.
- Changing the underlying methodology, formulas, thresholds, or the
  known-limitation status of the provisional risk features.

## Dependencies (pom.xml)

- `tech.tablesaw:tablesaw-core` (0.44.4) — CSV loading; API verified against
  the real jar and real project CSVs (`Table.read().csv(...)`,
  `intColumn`/`doubleColumn`/`stringColumn`/`dateTimeColumn` accessors,
  `sortOn`, `addColumns`, `DoubleColumn.create`/`StringColumn.create` all
  confirmed working against the actual `data/*.csv` files)
- `ml.dmlc:xgboost4j_2.12` (2.1.4) — same core engine as Python's `xgboost`.
  Bundles a `macos/aarch64` native library, but that native lib needs the
  OpenMP runtime (`libomp`) present on the host — confirmed via a real
  train/predict spike, which failed with `UnsatisfiedLinkError` until
  `brew install libomp` was run (now installed on this machine). **The
  README's setup section must document `brew install libomp` as a
  prerequisite on macOS**, or the pipeline fails to start.
- `org.junit.jupiter:junit-jupiter` (5.x) — tests
- No IsolationForest/SMOTE library dependency — both are hand-ported (see
  Non-goals rationale)
- **JFreeChart dropped.** A confusion matrix is a small annotated grid, not
  a chart type JFreeChart supports directly (would need a hand-rigged
  `XYBlockRenderer` + manual text annotations — more code and a dependency
  for something plain JDK does natively). `RunPipeline` renders
  `confusion_matrix.png` with `java.awt.image.BufferedImage` +
  `Graphics2D` + `ImageIO.write`, matching matplotlib's
  `ConfusionMatrixDisplay` layout (grid, per-cell counts, axis labels).

## Module-by-module mapping

**DataLoader** — Traced which columns the pandas merge chain
(`transactions.merge(users).merge(devices).merge(ips).merge(merchants).merge(chargebacks)`)
actually feeds into any downstream computation (feature engineering,
agents, orchestrator, evaluation). Verified (by grepping the whole
pipeline for every column name) that **`users`, `merchants`, and
`chargebacks` are joined in the Python version but none of their columns
(`user_age_days`, `email_risk`, `merchant_risk`, `chargeback_at`,
`chargeback_reason`) are ever read** — `is_fraud` comes directly from
`transactions_raw.csv`'s own `fraud_label` column, not from chargeback
presence. Also verified every join key (`device_id`, `ip_id`, `user_id`,
`merchant_id`, `transaction_id`) is unique in its source table (18000,
45000, 30000, 2000, 120000 rows respectively, all unique), so those joins
are 1:1 and never duplicate rows.

Given that, `DataLoader` only joins what's actually consumed: `devices`
(for `is_fraud_device_hint` via `device_id`) and `ips` (for
`ip_risk_level` via `ip_id`), via plain `HashMap` lookups built from each
table, applied while iterating `transactions_raw`. This is a scope
reduction, not a behavior change — the dropped columns were provably dead
weight in the original pipeline too, output is identical, and it removes
a meaningful amount of merge-suffix bookkeeping (`_x`/`_y` handling) for
columns nothing downstream reads. Result table still has all 120,000 rows
and includes: `transaction_id`, `user_id`, `created_at` (parsed
timestamp), `amount`, `sender_country` (`card_country`),
`receiver_country` (`country`), `is_fraud_device_hint`, `ip_risk_level`,
`is_fraud` (from `fraud_label`).

**FeatureEngineering** — `addComplianceFeatures` (cross-border flag,
per-country threshold map, compliance violation flag, synthetic
`message_type`/`purpose_code` via seeded random choice) and
`addDerivedRiskFeatures` (provisional `time_diff`/`velocity_score`/
`device_risk_score`, ported verbatim including the median-fill logic and
the `ip_risk_level_y`-or-`ip_risk_level` fallback).

**ml.IsolationForest** — Hand-port of sklearn's algorithm: random
feature/split subsampling per tree, binary isolation trees, average path
length `c(n)` normalization, anomaly score `2^(-E(h(x))/c(n))`,
contamination-based percentile threshold (default `0.02`, matching
`AnomalyAgent`'s current default).

**ml.SmoteTomek** — Hand-port combining SMOTE oversampling (k-NN based
interpolation between minority-class samples) and Tomek-link removal
(pairs of opposite-class nearest neighbors), matching imbalanced-learn's
approach and default `k_neighbors`.

**ml.TrainTestSplit** — Stratified 80/20 split preserving per-class
proportions, matching `train_test_split(..., test_size=0.2, stratify=y)`.

**agents.\*** — 1:1 port of each agent class: `AnomalyAgent` (wraps
`ml.IsolationForest`, same 3-feature input), `PolicyAgent` (passthrough of
`compliance_violation`), `RiskAgent` (`0.4/0.3/0.3` weighted composite),
`HumanAgent` (`amount > 20000` → reject), `AuditLayer` (SHA-256 of
`transaction_id + decision`, append-only log), `MLAgent` (wraps XGBoost4J
with the same hyperparameters: 300 estimators, max depth 8, learning rate
0.05, `scale_pos_weight` 10, seed 42, logloss eval metric).

**AcsOrchestrator** — Same training/prediction/fusion sequence: trains
anomaly + ML agents, computes anomaly/policy/risk columns, fuses per-row
with `0.75 * ml_score + 0.15 * anomaly_flag + 0.1 * policy_flag`, threshold
`0.8` → FLAGGED, human review → REJECTED, audit-logs every decision.

**Evaluate** — Confusion matrix and a classification-report equivalent
(precision/recall/F1/support per class, accuracy, macro/weighted avg) in
the same layout as sklearn's `classification_report`, plus decision-count
breakdown.

**RunPipeline** — Same sequence as `scripts/run_pipeline.py`: load → merge
→ engineer features → stratified split → SmoteTomek balance → orchestrator
run → evaluate → print + write `reports/confusion_matrix.png` (via
JFreeChart) and `reports/metrics_summary.txt` (same text format, including
the provisional-features caveat line).

## Testing

`PipelineTest.java` ports the three existing smoke tests: merged row count
is 120,000 and `is_fraud` column exists; engineered features add the
expected columns with `velocity_score`/`device_risk_score` in `[0,1]`; no
missing `time_diff` values. Additionally, given the hand-ported ML pieces
are new code (not a 1:1 line-for-line translation like the rest), each gets
a small focused unit test: `IsolationForest` flags an obviously synthetic
outlier, `SmoteTomek` balances a synthetic imbalanced set and produces no
duplicate-only oversampling, `TrainTestSplit` preserves class proportions
within tolerance.

## Verification plan

Run `RunPipeline` against the real `data/*.csv`, confirm it completes
without error and produces `reports/confusion_matrix.png` and
`reports/metrics_summary.txt` in the same format as today, with numbers in
a broadly similar range to the existing `[[19669,244],[4025,62]]` (exact
match not expected — see Non-goals). Run `mvn test` and confirm all tests
pass. Only after this passes does the Python source get removed.
